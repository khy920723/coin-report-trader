# M2 명세: AI 보고서

이 명세는 2단계 AI 보고서의 명세다(사용자 결정(2026-11-21)의 차례에서 8번 문서). 바탕은 제품 규칙(`docs/product-rules.md`, 아래 "N절"), 요구사항 명세서(`docs/requirements.md`, 아래 "REQ-…"), 1단계 보완 명세(`docs/specs/m1.md`, 아래 "M1 명세 N"), 구조 설계서(`docs/architecture.md`), 화면 설계서(`docs/screen-design.md`, 아래 "설계서 N"와 그 PPT `docs/screen-design/*.pptx`, 아래 "PPT 5-n"), `CLAUDE.md`다. 거기 있는 규칙과 모습은 옮기지 않고 가리킨다. 이 명세에 없는 약속은 M1 명세 그대로다.

M2(2단계 AI 보고서)는 고른 봉 단위의 봉이 끝날 때마다 회차를 돌려, 고른 코인마다 Claude Code 세션 하나로 AI 보고서를 만든다. 세션은 검색 판별, 봉 판별, 최종 예측의 세 부분을 서브 에이전트로 한 번씩 부른다. 2단계의 회차는 검사와 주문 없이 돈다(REQ-AI-026). exe에서 보이는 결과는 이렇다. 처음 설정이나 설정에서 네 칸의 모델과 노력 값을 고르면, 다음 봉이 끝난 뒤 보고서 화면에 코인마다 회차의 보고서가 보이고, 알림센터의 보고서 알림 탭에 코인마다 한 줄씩 쌓인다.

- 2단계의 1번(4절)은 M1 명세 4절의 1단계 보완 번호(31번~60번)가 모두 병합된 main에서 시작한다.
- 화면 설계서와 이 명세가 다르면 이 명세가 앞선다. 화면 설계서는 고치지 않는다. 화면 설계서의 원본은 PPT(`docs/screen-design/*.pptx`)다(`CLAUDE.md`의 문서 규칙). 2단계에 필요한 화면 항목은 3.12가 정하고, PPT의 '명세에 더할 것' 가운데 1·2단계의 것을 3.12.1~3.12.7에 넣었다. 자리는 PPT의 화면 번호(SCR-..)와 설계서의 지금 자리를 요구사항 8절대로 고쳐 읽어 쓴다.
- 팀이 만들고 시험하는 것은 모두 만든 숫자와 가짜로 한다. 세션과 CI는 진짜 `claude`를 부르지 않고 거래소 API도 부르지 않는다(`CLAUDE.md`). 진짜 `claude`로 하는 확인은 사용자 PC의 2단계 실물 시험(5절)이다.
- 이 명세가 쓰는 Claude Code의 명령과 옵션은 3.7.6의 공식 문서에서 확인한 것뿐이다. 확인하지 못한 것은 7절에 적었다.

## 1. 범위

넣는 것:

- 회차(3.5): 고른 봉 단위의 봉이 끝날 때마다 돈다(3절, REQ-AI-026, REQ-TRADE-016). 앞 회차가 끝나지 않았으면 건너뛰기, 끊긴 회차(10절), 코인 세션의 동시 실행(REQ-AI-003), 현재가를 읽지 못할 때 쉬기(REQ-AI-027), AI 끄기(REQ-AI-031, 8절의 버전 확인).
- 현재가 읽기(3.6): 거래의 `trading/quote/`가 맡는다.
- Claude Code 실행기(3.7): 실행 파일 찾기, 버전과 로그인 확인, 서브 에이전트 정의, 칸마다의 모델과 노력 값, 시간 제한과 끝내기, 토큰량과 걸린 시간 읽기(8절, REQ-AI-004, REQ-AI-022, REQ-AI-030, REQ-AI-034).
- 입력과 답의 CSV(3.8): 세 부분마다 열이 정해진 CSV(UTF-8 BOM). 검사와 실패(REQ-AI-010~REQ-AI-013, REQ-AI-029, REQ-AI-032, REQ-AI-033, REQ-DATA-010).
- 지난 판단의 결과(3.9): 예측 가격, 실제 값, 차이(%), 오름·내림이 맞았는지(8절, REQ-AI-018, REQ-AI-019, REQ-AI-028).
- 저장(3.10): 스키마 2. 회차, 보고서, 근거·출처·검증 목록의 표와 설정 키.
- 알림(3.11): A-2, A-17, A-18, A-19, A-26과 AI 쪽의 A-29, A-30(11절, REQ-ALERT-024).
- 화면(3.12): 보고서 화면, 처음 설정과 설정의 모델·노력 값 칸, 처음 설정의 글(REQ-USE-005, REQ-AI-035), 화면 설계서(PPT)의 1·2단계 것(3.12.4~3.12.7).

- 보안(3.13): AI에 주지 않는 것, 자료 속 지시를 따르지 않는 것, Claude 자격 정보를 다루지 않는 것(REQ-AI-034, REQ-MAINT-007).

- 안내 문서와 도움말 화면(3.16. 사용자 결정(2026-11-22). REQ-MAINT-012, REQ-UI-005): 저장소의 안내 문서 하나를 exe 묶음에 넣고, 앱 안의 도움말 창이 그 글을 보인다.

넣지 않는 것:

- 검사와 주문, 판단표, 계정 읽기와 대조, 손절과 한도, 멈춤과 긴급 정지, 상태 띠, 매매 방식 칸(3단계). 그래서 최종 예측의 매매 기록 요약은 줄이 없는 표다(3.8.4). 보고서 화면의 "이 판단으로 낸 주문"(설계서 5.2)도 3단계다.

- 보고서 화면의 모의매매·실거래 기록 고르기(설계서 5.2의 2. M6).
- 트레이, 시작 앱, 절전에서 돌아온 뒤의 처리, 놓친 회차(4단계. REQ-PC-004). 켠 직후의 네트워크 확인, 대조, 손절 점검, 놓친 회차(10절의 순서)는 그 기능이 생기는 단계가 더한다.
- exe 묶음 이름과 Git 태그(지휘의 일. REQ-MAINT-010). 판 번호를 올리는 것은 23번이다.
- API 키 방식(8절의 "나중에 더할 수 있다"). 실행기는 갈아 끼울 수 있게 `AiRunner`(3.4) 뒤에 둔다.
- 하루 최대 횟수의 셈(3단계의 하루 경계와 함께 쓴다). 2단계는 봉 단위로 정해지는 횟수를 넘지 않는다(3절).
- 실거래 전 모의 회차의 셈(REQ-LIVE-007, 5단계). 쉰 회차를 세지 않는다는 것(8절)은 그때 쓴다. 2단계는 회차의 상태(3.10)만 남긴다.
- DB를 바꾸기 전의 사본(REQ-MAINT-006, 4단계). 2단계는 스키마를 2로 올리지만 사본을 남기지 않는다.

## 2. 2단계에서만 쓰는 모습

아래는 2단계에서만 쓰는 모습이고 뒤 마일스톤이 바꾼다. 규칙은 바꾸지 않는다.

1. 회차의 일: 2단계의 회차는 봉 받기, 봉 통계, 현재가 읽기, AI 호출, 기록이다(2절의 회차, REQ-AI-026). 주문 정리, 검사와 주문은 없다. 그래서 2단계의 어느 보고서로도 주문이 나가지 않는다(REQ-AI-001, REQ-TRADE-003은 주문이 생기는 3단계에서 "그 회차 AI의 답을 따른다"로 이어진다).
2. 모드: 모드를 고르는 곳이 없다. 회차, 보고서, 알림의 모드는 모두 `Mode.PAPER`이고 화면과 디스코드의 글은 "모의매매"다(M1 명세 2의 5). 검증 목록과 기록은 모드마다 따로 두는 꼴로 저장한다(3.10). 실거래의 것이 생기는 것은 6단계다.
3. 알림의 글: 설계서 12의 A-2와 A-17의 글은 주문을 말한다. 2단계에는 주문이 없으므로 3.11의 글로 보인다. 알림 수는 화면 이름 목록의 "현황 ({n})"이다(M1 명세 2의 4, REQ-UI-003).
4. 걸린 시간: 3절의 두 걸린 시간 가운데 "주문을 낸 때까지(주문이 없으면 보고서까지)"는 2단계에 주문이 없으므로 "보고서까지"와 같은 값을 저장한다. 화면에는 "보고서까지"만 보인다(3.12.1). REQ-PERF-001의 둘째 값을 보이는 것은 3단계다.
5. 오류와 저장 실패 뒤(11절의 2단계): AI 보고서를 만들거나 저장하다 난 오류면 AI를 끄고 알린다(3.5.4). 봉 받기는 계속한다. 다른 곳의 오류는 M1 명세 2의 10처럼 알리고 계속한다.
6. 일시 차단: M1 명세 2의 3 그대로다(REQ-FETCH-006). 차단 중의 회차는 3.5.2의 1대로다.
7. 2단계 전에 처음 설정을 마친 기록: 처음 설정은 다시 보이지 않는다. 모델과 노력 값(6절, REQ-SETUP-004)은 설정 화면에서 고른다. 고르기 전에는 회차를 시작하지 않는다(3.5.2의 1). 보고서 화면에 그 까닭이 보인다(3.12.1). `first_setup_level`(M1 명세 3.7)은 "2" 그대로 쓴다.

모두 표준 라이브러리만 쓰는 frozen dataclass, `StrEnum`, `typing.Protocol`이다. 가격은 `Decimal`, 시각은 UTC가 붙은 `datetime`이다. 새 모듈은 `core/ai.py`이고, 화면이 받는 값은 `core/views.py`, 경계는 `core/ports.py`, 글은 `core/texts.py`에 더한다. 지금 코드의 이름과 겹치지 않는다(자료 스레드의 `_scheduled_round`는 봉 받기의 (라)이므로, 회차의 이름은 `report_round`로 쓴다).

### 3.5 회차(3절, 10절)

#### 3.5.1 회차의 때

- 회차의 봉 마감 시각 T: 고른 봉 단위의 봉이 끝나는 때다. 시계로 셈하고 봉이 왔는지로 정하지 않는다(3절). 2단계의 받는 때 (라)(M1 명세 3.5.3의 "봉이 끝나는 때 + 10초")가 곧 회차의 시작이다. 그 받기가 회차의 봉 받기다.
  - 예(만든 값): 60분봉이고 저장된 마지막 봉의 시작이 UTC 09:00이면, 봉이 끝나는 때는 10:00, (라)는 10:00:10이다. 이 회차의 T는 10:00이다.
- 다음 회차 때: T + 단위의 길이다(`CANDLE_UNIT_LENGTHS`). 최종 예측의 "다음 예정 시각"(8절)과 예측 가격이 가리킨 때(3.9)가 이 때다.
- (가)·(나)·(다)의 받기(M1 명세 2의 1)와 일시 차단이 풀린 뒤 저절로 한 번 받는 받기(M1 명세 2의 3)는 회차가 아니다. 봉 통계만 새로 한다(REQ-FETCH-002, 요구사항 8절). 회차는 그 뒤의 (라)의 때부터 돈다.
- 시각 목록은 없다(REQ-TRADE-016). 2단계의 회차는 봉 마감 때에만 돈다. 켠 직후에 한 번 도는 놓친 회차는 4단계다(REQ-PC-004).

#### 3.5.2 한 회차의 차례

자료 스레드가 맡는다. 세션은 AI 스레드가 기다린다. AI 스레드는 코인 세션마다 하나씩 `app`이 만드는 daemon 스레드이고, `AiRunner.run`을 부르고 그 결과를 자료 스레드의 큐에 넣고 끝난다. AI 스레드는 DB를 열지 않고 Qt 객체를 만지지 않는다.

1. 회차를 시작하는지 본다((라)의 받기가 끝난 뒤). 아래 가운데 하나면 회차를 시작하지 않는다. 번호를 주지 않고 표에 쓰지 않으며 로그에만 남긴다.
   - 처음 설정 전, 설정을 읽지 못한 동안, 봉 단위가 저장되지 않은 동안(M1 명세 3.8, 3.5.4).
   - 네 칸(`AiSlot`)의 모델과 노력 값이 다 저장되지 않음(6절의 "없으면 시작 못 함").
   - AI가 꺼짐(`AiStatus.ERROR_OFF`. 3.5.4).
   - 일시 차단 중이라 (라)의 받기를 요청하지 않음(M1 명세 3.8의 "차단 중의 (라)의 때").
   - 앞 회차가 끝나지 않음(그 회차에 `RUNNING`인 보고서가 있음. 3절의 "건너뛴다").
2. `AiRunner.check()`를 부른다(8절의 "호출 전에"). 결과에 따라:
   - `NOT_FOUND`, `VERSION_UNREADABLE`, `VERSION_OUT_OF_RANGE`: AI를 끄고(`AiStatus.NOT_FOUND`나 `VERSION_OFF`) A-19(3.11)를 만들고 회차를 시작하지 않는다. 다음 (라)의 때에 다시 본다. 범위 안이 되면 `AiStatus.ON`으로 돌아오고 그 회차부터 돈다(버전으로 끈 AI는 "호출 전에" 다시 확인한다는 8절을 따른 것이다).
   - `LOGGED_OUT`: 회차를 시작하되, 3의 코인마다 세션을 띄우지 않고 보고서를 `FAILED`(`FailureKind.LOGGED_OUT`)로 쓴다. A-18 하나(코인 없음)를 만들고 A-17은 만들지 않는다(8절의 "로그인 만료는 다른 실패와 구분해 알린다").
   - `READY`: 3으로 간다.
3. 회차를 쓴다: 표 `rounds`(3.10)에 모드, 번호(그 모드의 가장 큰 번호 + 1, 처음은 1), 계기, 봉 단위, T, 다음 회차 때, 시작한 때를 쓰고 상태는 `running`이다.
4. 코인마다(설정 목록의 차례):
   - 그 코인의 (라)의 받기가 실패했거나(봉을 새로 받지 못함) 봉 통계가 셈해지지 않았으면(`NO_DATA`나 통계 셈의 실패) 보고서를 `SKIPPED`(`SkipReason.NO_STATS`)로 쓴다. 알림은 그 받기가 만든 A-1(M1 명세 3.8의 "한 받기의 알림"과 되풀이)뿐이고 새로 만들지 않는다(3절의 "알린다"는 A-1이다).
   - 아니면 현재가를 읽는다(3.6. 세션을 띄우기 바로 전. REQ-AI-009). 읽지 못하면(`QuoteError`) 보고서를 `SKIPPED`(`SkipReason.NO_PRICE`)로 쓰고 A-2(3.11)를 만든다. AI를 부르지 않는다(REQ-AI-027). 일시 차단 중이면 요청하지 않고 같다(오류 이름 "일시 차단"). `get_price`가 `QuoteError`가 아닌 예외를 내면 A-2가 아니고 3.5.4의 예상하지 못한 예외다(A-30과 `ERROR_OFF`).
   - 읽으면 지난 판단의 결과(3.9)와 입력 파일(3.8)을 만들고, 보고서를 `RUNNING`으로 쓴 뒤(현재가와 읽은 때를 담는다) AI 스레드를 띄운다. 앞 코인의 세션을 기다리지 않는다. 그래서 고른 코인의 세션이 함께 돈다(REQ-AI-003).
   - 봉 판별에 주는 봉 통계는 그 코인의 (라)의 받기가 셈해 `CoinView.stats`로 화면에 보낸 바로 그 `BarStats`다. 다시 셈하지 않는다(REQ-STAT-004, REQ-AI-008).
5. 세션 결과를 받으면(자료 스레드의 큐): 답을 검사하고(3.8.5) 보고서를 `OK`나 `FAILED`로 고쳐 쓴다. 토큰량, 끝난 때, 걸린 시간(3.7.5)을 함께 쓴다. `OK`면 A-26, `FAILED`면 A-17이나 A-18(3.11)을 만든다. 그 코인의 `ReportListView`를 보낸다.
   - 답을 검사하기 전에, `FAILED`이면 `check()`를 한 번 더 불러 `LOGGED_OUT`이면 실패 종류를 로그인 만료로 본다(3.7.5). `TIMEOUT`과 `LIMIT`에는 `check()`를 부르지 않는다.
   - 시간 제한을 넘긴 세션의 답은 쓰지 않는다(8절의 "늦게 온 답으로는 주문하지 않는다"). 실행기가 끝낸 뒤 돌아오는 `TIMEOUT`에는 답이 없다.
6. 그 회차의 보고서가 모두 `RUNNING`이 아니게 되면 회차의 상태를 `done`으로, 끝난 때를 쓴다.

- 코인 세션 하나의 결과는 다른 코인의 세션을 기다리지 않고 처리한다. 보고서 알림은 코인마다 그 코인의 보고서가 다 써졌을 때 생긴다(3절 4, REQ-ALERT-024).
- 회차가 도는 동안의 설정 저장: 받는다. 도는 세션은 그대로 끝나게 두고, 바뀐 값은 다음 회차부터 쓴다. 코인을 빼도 도는 그 코인의 보고서는 쓴다.
- AI 호출 수로 회차를 막지 않는다(REQ-AI-021).
- 끝낼 때: 이벤트 루프가 끝나면 `AiRunner.stop_all()`을 부르고 기다리지 않는다(M1 명세 3.8의 "끝낼 때"). 도는 회차는 다음에 켤 때 끊긴 회차가 된다(3.5.3).
- 회차의 예(만든 값): 코인 `KRW-AAA`, `KRW-BBB`, 60분봉. 10:00:10에 두 코인을 받는다. `KRW-AAA`는 받기와 통계가 되고 현재가 100을 읽어 세션을 띄운다. `KRW-BBB`는 받기가 "네트워크 끊김"으로 실패해 `SKIPPED`(봉 통계를 만들지 못함)이고 알림은 그 받기의 A-1 하나다. `KRW-AAA`의 세션이 정상으로 끝나면 그 보고서는 `OK`, A-26 하나가 생기고 회차는 `done`이다.

#### 3.5.3 끊긴 회차(10절)

- 끊긴 회차: 켤 때 자료 스레드는 차례의 맨 앞(M1 명세 3.8의 켤 때 차례 1보다 앞. DB를 연 직후)에서 상태가 `running`인 회차를 `interrupted`로, 그 회차의 `RUNNING` 보고서를 `INTERRUPTED`로 고쳐 쓴다. 다시 돌리지 않는다(10절). 세션 폴더(3.7.2)의 남은 것을 모두 지운다.
- 끊긴 회차의 표시(`interrupted`, `INTERRUPTED`)는 3.5.2의 1의 건너뛰기 판정(`RUNNING` 보고서가 남았는지)이 켠 뒤에 막히지 않게 하는 데도 쓰인다.
- 놓친 회차는 4단계다(REQ-PC-004, REQ-TRADE-016). 2단계는 켤 때 회차를 돌리지 않고, 꺼져 있던 동안의 봉 마감 때를 세지 않는다. 켠 뒤의 첫 회차는 처음 오는 (라)의 때다. 10절의 "네트워크 확인 → 대조 → 손절 점검 → 놓친 회차"는 2단계에 하나도 없고, 그 기능의 단계가 더한다.

#### 3.5.4 AI 끄기

- 끄는 까닭과 다시 켜는 때:

| 까닭 | `AiStatus` | 알림 | 다시 도는 때 |
|---|---|---|---|
| 네 칸을 다 고르지 않음 | `NOT_CHOSEN` | 없음 | 네 칸을 저장한 때 `check()`를 불러 바꾼다(아래). 그 뒤의 다음 회차부터 돈다 |
| 실행 파일을 찾지 못함, 버전을 읽지 못함 | `NOT_FOUND` | A-19 | `check()`가 `READY`인 다음 회차 |
| 버전이 범위 밖 | `VERSION_OFF` | A-19 | 같음 |
| AI 보고서를 만들거나 저장하다 오류(아래) | `ERROR_OFF` | A-30이나 A-29 | 프로그램을 다시 켰을 때(REQ-AI-031) |

- `ERROR_OFF`로 끄는 일(11절의 2단계, REQ-AI-031): 3.5.2의 2~6 안에서 난 예상하지 못한 예외(실행기 `run`이 낸 예외, 입력 파일 만들기와 답 검사의 예외 포함)와 보고서·회차 표의 쓰기 실패(`StorageError`)다.
  - 예상하지 못한 예외면 A-30(단계 "AI 보고서"), 쓰기 실패면 A-29(단계 "보고서 저장")를 만든다. 요구사항 8절의 "2단계는 AI 쪽 오류면 AI만 끄고"를 따라 저장 실패도 끈다.
  - 그 코인의 보고서는 쓸 수 있으면 `ERROR`(실패 글은 오류 이름)로 쓴다.
  - 끈 뒤에는 새 세션을 띄우지 않는다. 이미 도는 세션은 끝나게 두고, 그 결과는 보통처럼 처리한다(저장이 되면 쓴다).
  - 봉 받기와 A-1 등 1단계의 일은 그대로 한다(REQ-AI-031).
  - 현재가 읽기의 `QuoteError`(A-2)와 실행기가 알린 실패(8절의 다섯)는 끄지 않는다.
- `AiStatus`가 바뀔 때마다 `AiStatusView`를 보낸다. 켤 때 차례 5에서 처음 하나를 보낸다. 그때 네 칸이 다 저장되어 있으면 `check()`를 부르고(시작할 때의 버전 확인. 8절), `READY`이거나 `LOGGED_OUT`이면 `ON`이다. 네 칸이 다 저장되어 있지 않으면 `check()`를 부르지 않고 `NOT_CHOSEN`이다. 그래서 네 칸을 저장하지 않는 시험은 실행기를 부르지 않는다(3.15).
- 네 칸을 저장한 때: `save_settings`로 네 칸이 모두 저장되면(저장이 성공한 뒤) 그때 `check()`를 부른다. `READY`나 `LOGGED_OUT`이면 `ON`이고, 그 밖은 3.5.2의 2대로(`NOT_FOUND`나 `VERSION_OFF`, A-19) 한다. 바뀌면 `AiStatusView`를 보낸다. 그래서 다음 봉이 끝나기 전에 보고서 화면의 맨 위 줄이 바뀐다(5절의 실물 시험 2). `ERROR_OFF`이면 부르지 않는다(다시 켤 때까지 꺼져 있다). 네 칸이 다 저장되지 않은 저장에서는 부르지 않는다.

### 3.6 현재가 읽기(`trading/quote/`, 거래)

- 진짜: `HttpQuoteSource`가 `PriceSource.get_price(market)`를 갖춘다. 요청 경로는 `/v1/ticker`(마켓 코드 하나)이고 값은 최근 체결가다(2절의 현재가). 응답 변환과 오류 이름은 M1 명세 3.9 그대로다(응답을 읽지 못하면 "응답 형식 오류").
- 감싸는 부품: `QuoteClient.read_price(market: str) -> Decimal`. 요청 한 번이고 봉 받기와 같은 요청 한도 장치를 쓴다(M1 명세 3.10). 실패하면 `QuoteError`를 그대로 내고 그 자리에서 다시 보내지 않는다. 소스가 `PriceSource`가 아니면 `TypeError`다.
- 일시 차단을 받으면 `app`이 M1 명세 2의 3대로 `blocked_until`을 정한다. 그 회차의 뒤 코인은 요청하지 않고 `SKIPPED`(현재가를 읽지 못함, 오류 이름 "일시 차단")다.
- 가짜: `tests/fakes/quote.py`의 가짜 시세에 `get_price`를 더한다(코인마다 정한 값이나 정한 `QuoteError`). 업비트의 실제 응답과 문서의 예시를 시험에 넣지 않는다(REQ-MAINT-007).

### 3.7 Claude Code 실행기(`ai/`, 백엔드)

앱은 사용자가 설치하고 Anthropic의 로그인 흐름으로 로그인한 그대로의 `claude` 실행 파일만 부른다(8절, REQ-AI-034). 앱에는 로그인 화면이 없고, Claude 자격 정보나 세션 토큰(그 파일 포함)을 읽거나 저장하거나 옮기지 않는다. API 키를 넣지 않는다(REQ-AI-005).

#### 3.7.1 실행 파일 찾기와 확인(`check()`)

- 찾기: `command`(3.4)가 주어지면 그것을 쓰고 찾지 않는다(시험). `None`이면 환경 변수 `PATH`를 `os.pathsep`으로 나눈 항목 가운데 절대 경로인 항목만 차례로 보아, 그 폴더의 `claude.exe`(Windows)나 `claude`(그 밖. 실행할 수 있는 파일)를 처음 찾은 것을 쓴다. 지금 폴더와 상대 경로 항목은 보지 않는다. `shutil.which`는 쓰지 않는다: Windows에서는 `PATH`보다 지금 폴더를 먼저 볼 수 있어, 풀어 둔 앱 옆의 `claude.exe`가 돌 수 있다. 찾지 못하면 `NOT_FOUND`다. 다른 자리를 뒤지지 않는다(7절).
  - `.cmd`와 `.bat`(npm 설치가 두는 감싼 파일)은 부르지 않는다. 배치 파일은 `cmd.exe`가 인자를 다시 읽으므로 셸을 거치지 않는다는 약속(3.7.2)이 깨진다. 권하는 설치는 기본 설치(native)이고(setup 문서), Windows의 기본 설치는 `claude.exe`를 둔다(changelog의 Windows 자동 업데이트 고침들). 그래서 PATH에 `claude.cmd`만 있으면 `NOT_FOUND`이고, A-19의 글과 내용은 3.11 그대로다("Claude Code를 설치하고 로그인했는지 확인하세요.").
- 환경과 띄우는 법: `check()`의 두 명령도 3.7.2의 환경(지운 변수와 넣은 변수)으로 부르고, 3.7.2의 `run()`과 같게 띄운다: Windows에서 `CREATE_NO_WINDOW`, 표준 입력 닫음, 작업 개체(Windows가 아니면 새 프로세스 묶음). exe는 콘솔이 없으므로(`packaging/`의 `.spec`의 `console=False`) 그러지 않으면 켤 때, 회차마다, `FAILED` 뒤마다 콘솔 창이 번쩍일 수 있다.
- 버전: `claude --version`을 부른다(시간 제한 30초). 표준 출력에서 처음 나오는 `숫자.숫자.숫자`를 버전으로 읽는다. 못 읽거나 끝 코드가 0이 아니면 `VERSION_UNREADABLE`이다.
- 시험한 버전 범위: `CLAUDE_VERSION_MIN` 이상, `CLAUDE_VERSION_LIMIT` 미만이다(3.4). 밖이면 `VERSION_OUT_OF_RANGE`다.
  - 하한 2.1.314: 이 명세가 쓰는 `--agents`의 파일 꼴이 2.1.281부터이고, 노력 값의 "Invalid effort level" 오류가 2.1.314에서 고쳐졌다(3.7.6의 문서).
  - 상한 2.2.0(미만): 2단계 실물 시험에서 쓴 버전이 이 범위 안인지 확인한다. 밖이면 범위를 고친다(7절).
  - 이번 고침에서 범위를 다시 보았고 그대로 둔다. 이 명세가 새로 쓰는 것이 생긴 판은 모두 하한 아래다: `--restricted` 2.1.248, `CLAUDE_CODE_SUBAGENT_MODEL_FORCE` 2.1.257, 서브 에이전트의 `omitClaudeMd` 2.1.271, `--tools`와 `--restricted`가 나중에 붙는 도구에도 걸리게 고친 것 2.1.295(3.7.6의 changelog). `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS`는 2.1.4부터다. 확인한 문서의 마지막 판(2.1.330)은 상한 안이다.
- 로그인: `claude auth status`를 부르고(시간 제한 30초) 끝 코드만 본다. 0이면 로그인됨, 1이면 `LOGGED_OUT`이다. 그 밖의 끝 코드와 시간 초과도 `LOGGED_OUT`으로 본다. 표준 출력과 표준 오류는 읽어 버리고, 저장하거나 로그에 쓰지 않는다(그 JSON에는 계정의 글이 들 수 있다).
- 차례: 찾기 → 버전 → 로그인. 앞이 안 되면 뒤를 하지 않는다.

#### 3.7.2 한 번의 실행(`run()`)

- 세션 폴더: 자료 폴더 `root`(M0 명세 3.5) 아래 `ai-sessions\{key}`다. `key`는 `r{회차 id}-{코인 기호}`(예: `r12-AAA`)다. 실행 전에 빈 폴더로 만들고(남은 것이 있으면 지운다), 입력 파일(3.8)과 `agents.json`(3.7.3)만 쓴다. 이것이 8절의 "프로그램이 관리하는 빈 폴더"다. 세션이 끝나면(어떻게 끝나든) 폴더를 지운다. 지우지 못하면 로그에만 남기고 다음에 켤 때 지운다(3.5.3).
- 명령(셸을 거치지 않고 인자 목록으로 부른다. 작업 폴더는 세션 폴더):

```
claude -p "<코인 세션 지시>"
  --output-format stream-json
  --verbose
  --json-schema "<3.7.5의 스키마>"
  --model <코인 세션 칸의 모델>
  --effort <코인 세션 칸의 노력 값>
  --agents agents.json
  --tools "Agent,Read,WebSearch"
  --allowedTools "Agent,WebSearch"
  --permission-mode dontAsk
  --restricted
  --no-session-persistence
  --strict-mcp-config
  --disable-slash-commands
```

  - `--tools`는 이 세션이 쓸 수 있는 도구를 셋으로 줄인다. `WebFetch`(페이지 본문 읽기)가 들지 않는다(8절, REQ-AI-006).
  - `--allowedTools`에는 `Agent`와 `WebSearch`만 둔다. `Read`는 넣지 않는다: `--allowedTools`의 `Read`는 작업 폴더 밖의 파일도 묻지 않고 읽게 하므로(headless 문서의 'Auto-approve tools'), 검색 결과에 숨은 지시가 사용자 폴더의 파일을 읽어 답에 옮길 수 있다(8절의 "주어진 파일 읽기", REQ-AI-034). `dontAsk`에서는 작업 폴더 안의 파일 읽기는 허가 없이 되고, 묻게 될 호출(작업 폴더 밖의 읽기)은 거절된다(같은 문서). 그래서 세 서브 에이전트의 `Read`는 세션 폴더의 입력 파일만 읽는다.
  - `--restricted`는 파일 도구를 작업 폴더에 가두고, 사용자와 프로젝트의 설정(훅 포함)을 싣지 않고 관리 설정과 `--settings`만 싣는다. 명령이나 코드를 돌리는 도구와 `WebFetch`도 뺀다(cli-reference 문서. 2.1.248부터). 이 둘로 읽기를 막으므로 `--setting-sources`는 쓰지 않는다.
  - `--output-format stream-json`은 줄마다 JSON 하나를 낸다(3.7.5). headless 문서의 stream-json 예는 모두 `--verbose`와 함께 쓰므로 같이 준다.
  - `--strict-mcp-config`는 사용자가 둔 MCP 서버를 싣지 않고, `--disable-slash-commands`는 스킬과 명령을 끈다. `--no-session-persistence`는 세션을 디스크에 남기지 않는다.
  - `--bare`는 쓰지 않는다. 문서에 따르면 bare 모드는 구독 로그인을 쓰지 않는다(8절의 구독 로그인과 맞지 않는다).
- 코인 세션 지시(`ai/agents.py`의 글. 한국어): 세 서브 에이전트 `search_judge`, `candle_judge`, `final_predictor`를 이 차례로 한 번씩 부르고, 다른 일(파일 읽기, 검색)은 스스로 하지 않는다(REQ-AI-025). Agent 도구로 서브 에이전트를 부를 때 model과 effort를 넘기지 않는다(넘긴 모델은 서브 에이전트 정의의 `model`보다 앞선다. sub-agents 문서). 두 판별의 답을 받으면 `final_predictor`를 부르는 글에 두 답의 CSV 글을 그대로 붙인다(8절의 "두 판별의 결과와 근거"). 두 판별 가운데 하나라도 3.8.5의 판별 실패이면 `final_predictor`를 부르지 않는다. 마지막에 세 부분의 답을 3.7.5의 필드에 고치지 않고 그대로 담는다. 아래 3.13의 지시 글이 든다.
- 환경 변수(8절의 "인증용 환경변수를 지운다"): 앱의 환경을 복사한 뒤 `ANTHROPIC_API_KEY`, `ANTHROPIC_AUTH_TOKEN`, `CLAUDE_CODE_OAUTH_TOKEN`을 지운다. 8절의 구독 로그인을 지키려고, 모델 제공자를 바꾸는 변수(`CLAUDE_CODE_USE_BEDROCK`, `CLAUDE_CODE_USE_VERTEX`, `CLAUDE_CODE_USE_FOUNDRY`, `CLAUDE_CODE_USE_MANTLE`, `CLAUDE_CODE_USE_ANTHROPIC_AWS`, `CLAUDE_CODE_USE_ANTHROPIC_GOOGLE_CLOUD`, `CLAUDE_CODE_PROVIDER_MANAGED_BY_HOST`), 접속 주소를 바꾸는 변수(`ANTHROPIC_BASE_URL`, `ANTHROPIC_BEDROCK_BASE_URL`, `ANTHROPIC_BEDROCK_MANTLE_BASE_URL`, `ANTHROPIC_VERTEX_BASE_URL`, `ANTHROPIC_FOUNDRY_BASE_URL`, `ANTHROPIC_AWS_BASE_URL`, `ANTHROPIC_GOOGLE_CLOUD_BASE_URL`), 다른 제공자와 프로필의 인증 변수(`ANTHROPIC_AWS_API_KEY`, `ANTHROPIC_FOUNDRY_API_KEY`, `ANTHROPIC_FOUNDRY_AUTH_TOKEN`, `AWS_BEARER_TOKEN_BEDROCK`, `ANTHROPIC_PROFILE`)도 지운다(env-vars 문서, authentication 문서의 'Authentication precedence': 제공자 변수와 `ANTHROPIC_PROFILE`은 구독 로그인보다 앞선다). 네트워크 프록시(`HTTPS_PROXY` 등)는 지우지 않는다. 사용자가 고른 노력 값이 덮이지 않게 `CLAUDE_CODE_EFFORT_LEVEL`도 지운다(문서: 이 변수는 서브 에이전트의 `effort`보다 앞선다). 사용자가 고른 모델이 덮이지 않게 `CLAUDE_CODE_SUBAGENT_MODEL_FORCE`도 지운다(문서: 켜져 있으면 서브 에이전트 정의의 `model`을 무시한다). 그리고 `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`을 넣는다(문서: 서브 에이전트를 배경으로 옮기지 않는다). 그래서 코인 세션은 세 서브 에이전트가 끝나기를 기다린 뒤 답을 낸다. 지우고 넣는 목록은 `ai/claude_env.py` 한곳에 두고, `run()`과 `check()`가 같이 쓴다(3.13의 검사).
- Windows: 콘솔 창이 뜨지 않게 `CREATE_NO_WINDOW`로 띄운다. 세션 프로세스는 닫히면 그 안의 프로세스를 모두 끝내는 작업 개체(Job Object, `JOB_OBJECT_LIMIT_KILL_ON_JOB_CLOSE`)에 넣는다. 그래서 앱이 죽어도 `claude`와 그 자식이 남지 않는다. Windows가 아닌 곳(시험)에서는 새 프로세스 묶음으로 띄운다.
- 표준 입력은 닫는다. 표준 출력은 끝까지 읽고(3.7.5), 표준 오류는 앞의 2,000자만 `redact`를 거쳐 `detail`에 쓴다. `detail`은 로그에만 쓴다(3.13).

#### 3.7.3 서브 에이전트 정의(`agents.json`)

`--agents`의 파일 꼴이다. 키는 에이전트 이름, 값은 정의다. 쓰는 필드는 문서의 CLI 정의 필드 가운데 `description`, `prompt`, `tools`, `model`, `effort`, `omitClaudeMd`뿐이다. `omitClaudeMd`는 셋 모두 `true`다: 서브 에이전트가 사용자·프로젝트·로컬의 CLAUDE.md 없이 시작한다(sub-agents 문서. 2.1.271부터. 관리 정책 파일은 싣는다).

| 이름 | `tools` | `model`, `effort` | `prompt`(한국어)의 내용 |
|---|---|---|---|
| `search_judge` | `"Read,WebSearch"` | 검색 판별 칸 | 그 코인에 대해 웹을 검색해 긍정이나 부정을 가린다. 검색 결과(제목, 주소, 요약)만 보고 페이지 본문을 열지 않는다. 입력은 세션 폴더의 `search_input.csv`이고 `Read`로 읽는다. 답은 3.8.2의 두 표 |
| `candle_judge` | `"Read"` | 봉 판별 칸 | `candle_stats.csv`(봉 통계 한 줄)만 읽고 다음 봉 하나 동안 오름이나 내림을 가린다. 검색하지 않는다. 답은 3.8.3의 두 표 |
| `final_predictor` | `"Read"` | 최종 예측 칸 | 3.8.4의 입력 파일 넷과 두 판별의 답을 읽는다. 앞 회차의 근거를 하나씩 견주고, 검증 목록을 고쳐 쓰고, 결과 글을 쓴 뒤 방향 예측, 예측 가격과 그 까닭, 제안가를 낸다(8절의 답 순서). 검색하지 않는다. 답은 3.8.4의 두 표 |

- 세 `prompt`에는 모두 3.13의 지시 글, 답 표의 머리줄(그대로 적는다), 글의 길이와 줄 수(3.8), "장기 보유나 단기 매매에 대한 의견 글을 쓰지 않는다"(REQ-AI-023)가 든다.
- `model`은 그 칸의 `CLAUDE_MODELS` 값, `effort`는 `Effort` 값이다(REQ-AI-004). 코인 세션 칸의 값은 명령의 `--model`, `--effort`로 준다(3.7.2).
- `search_judge`의 `Read`: 코인 세션은 파일을 읽지 않고(3.7.2) 두 판별의 답만 `final_predictor`에 붙이므로, 검색 판별은 제 입력을 스스로 읽는다. 읽는 곳은 세션 폴더(작업 폴더)뿐이다. 작업 폴더 밖의 읽기는 지금의 권한 설정이 막는다(`--allowedTools`에 `Read`가 없고 `dontAsk`, `--restricted`. 3.7.2).
- 부분마다 노력 값이 실제로 따로 쓰이는지는 2단계 실물 시험에서 확인한다(8절. 7절).

#### 3.7.4 시간 제한과 끝내기(REQ-AI-030)

- 값: 코인 세션 하나에 `SESSION_TIMEOUT_SECONDS` 900초(15분)를 건다(8절이 명세에 맡긴 값). 가장 짧은 봉 단위(30분봉)의 주기의 절반이라, 늦어도 다음 봉 마감 전에 회차가 끝난다.
- 재는 법: 실제 흐른 시각(8절)이다. 실행기는 프로세스를 띄운 때부터 `time.monotonic()`으로 재고, `Clock`(가짜 시계)으로 재지 않는다.
- 넘으면: 작업 개체를 끝내(Windows. 아니면 프로세스 묶음에 `SIGKILL`) 세션의 프로세스를 모두 끝낸다. 끝나기를 5초까지 기다린 뒤 `SessionResult(outcome=TIMEOUT)`를 돌려준다. 답은 담지 않는다. 재시도는 하지 않는다(8절).
- `check()`의 두 명령은 30초씩이고, 넘으면 같은 꼴로 끝낸다.

#### 3.7.5 결과 읽기

- 출력: `--output-format stream-json`의 줄마다 JSON 객체 하나다. 읽는 것은 아래 둘뿐이다. 그 밖의 줄과 키, 도구의 입력 값(검색어, 파일 이름 등), 도구의 결과, 글은 저장하지 않는다.
  - 마지막 `result` 줄(`type`이 `"result"`. 문서: stream의 마지막 줄은 result 메시지다)의 아래 키:
    - `structured_output`: 아래 스키마의 객체. 없으면 정한 꼴의 답이 없는 것이다(문서: 정한 꼴로 끝나지 못하면 이 필드가 없다).
    - `is_error`: 참이면 실패다.
    - `result`: 한도 초과를 가리는 데만 읽는다(아래). 저장하거나 로그에 쓰지 않는다.
    - `modelUsage`: 모델 이름에서 `inputTokens`, `outputTokens`, `cacheReadInputTokens`, `cacheCreationInputTokens`로. 문서에 따르면 서브 에이전트의 사용량이 든 세션 전체의 값이다(`usage`는 주 세션만이라 쓰지 않는다).
  - `assistant` 줄의 `tool_use` 블록: 도구의 이름(`name`)과 `id`, `parent_tool_use_id`. 이름이 `Agent`이면 입력의 `subagent_type`도 읽는다(어느 부분인지 가리는 데만 쓰고 저장하지 않는다).
- 쓴 도구(`SessionResult.tools`. REQ-AI-006, REQ-AI-025의 회차의 기록): `parent_tool_use_id`가 `null`인 `tool_use`는 코인 세션(`AiSlot.SESSION`)의 것이다. 그 밖은 그 값과 같은 `id`의 `Agent` 호출이 부른 서브 에이전트의 것이다(headless 문서의 'Follow subagent messages'). 그 `Agent` 호출의 `subagent_type`이 `search_judge`, `candle_judge`, `final_predictor`이면 검색 판별, 봉 판별, 최종 예측의 칸이고, 그 밖의 값이거나 찾지 못하면 코인 세션의 칸에 넣는다. 칸마다 처음 쓴 차례로, 겹치지 않게 이름만 담는다. 쓰지 않은 칸은 빈 튜플이다. 예(만든 값): `{session: ("Agent",), search: ("Read", "WebSearch"), candle: ("Read",), final: ("Read",)}`. 실패한 세션에서도 읽은 줄까지 담는다.
- `--json-schema`의 스키마(`ai/agents.py`의 `ANSWER_SCHEMA`): 객체이고 필드는 아래 여섯이며, 값은 모두 글(BOM 없는 CSV 글)이다. `additionalProperties`는 거짓이고, 필수는 앞의 넷이다(최종 예측은 두 판별이 실패하면 없다).

| 필드 | 담는 것 |
|---|---|
| `search_judgment` | 3.8.2의 판단 표 |
| `search_rows` | 3.8.2의 줄 표 |
| `candle_judgment` | 3.8.3의 판단 표 |
| `candle_rows` | 3.8.3의 줄 표 |
| `final_rows` | 3.8.4의 줄 표(판단 표보다 앞. 8절의 답 순서) |
| `final_judgment` | 3.8.4의 판단 표 |

- `SessionResult`를 만드는 법:
  - 시간 제한을 넘김: `TIMEOUT`.
  - 끝 코드 0이고 `result` 줄을 읽었고 `is_error`가 거짓이고 `structured_output`이 있음: `ANSWERED`. `answers`는 그 필드들이다.
  - `result` 줄의 `is_error`가 참이고 `result` 글에 "You've hit your "가 들었음: `LIMIT`. 구독 사용 한도에 닿았다는 Claude Code의 글이다(errors 문서의 'Usage limits': "You've hit your session limit · resets …" 등). 끝 코드는 보지 않는다.
  - 그 밖: `FAILED`. `detail`은 끝 코드, `is_error`, 표준 오류의 앞부분을 가린 글이다(`result` 글은 넣지 않는다).
  - 토큰량은 `result` 줄을 읽었으면(실패여도) 담는다. `tokens`는 `modelUsage`의 모델마다의 값을 더한 것이고, `model_tokens`는 모델마다 그대로다. 앱은 셈을 바꾸지 않고 Claude Code가 알려 준 값을 그대로 적는다(8절).
- 실패 종류(3.8.5의 답 검사 전): `TIMEOUT`은 시간 초과, `LIMIT`은 한도 초과다(`check()`를 부르지 않는다). `FAILED`는 `check()`가 `LOGGED_OUT`이면 로그인 만료(3.5.2의 5), 아니면 형식 오류다. 한도 초과는 앱의 문제가 아니므로 A-17의 내용 글이 그렇게 적는다(3.11).
- 부분마다의 토큰량: 문서의 값은 모델마다이고 부분마다가 아니다. 그래서 2단계는 세션 전체만 보이고(REQ-AI-022의 "안 되면 세션 전체만"), 모델마다의 값은 저장해 둔다(3.10). 부분마다 나눠 잴 수 있는지는 실물 시험에서 확인한다(7절).
- 걸린 시간(3절): 보고서를 `OK`, `FAILED`, `ERROR`로 고쳐 쓰는 때의 `Clock.now()`에서 그 회차의 T를 뺀 초(버림)다. 예(만든 값): T가 10:00:00이고 10:03:25에 썼으면 205초이고 화면은 "3분 25초"다. 걸린 시간으로는 알리지 않는다(REQ-PERF-001).
- 토큰의 예(만든 값): `modelUsage`가 모델 둘이고 입력 1,000과 500, 출력 200과 100, 캐시 읽기 0과 300이면 `tokens`는 입력 1,500, 출력 300, 캐시 읽기 300, 캐시 만들기 0이다.

#### 3.7.6 확인한 문서

#### 3.8.1 공통 꼴

- 파일: UTF-8 BOM, 쉼표로 나눔, 줄 끝은 CRLF, 첫 줄은 머리줄이다. 표준 라이브러리 `csv`의 기본 꼴(필요할 때만 큰따옴표)이다. 엑셀로 열린다.

  - `final_trades.csv`: `market`, `kind`(`최근 체결 가격`, `평균 매수가`, `체결되지 않고 끝난 주문 가격`), `price`, `utc`. 2단계는 머리줄뿐이다(2의 1).

- 두 판별의 답은 코인 세션이 부르는 글에 붙여 넘긴다(3.7.2).
- 답의 판단 표(한 줄. 열의 차례가 8절의 답 순서다. 결과 글을 이번 판단과 같은 호출에서 받는다. REQ-AI-017): `market`, `result_text`(지난 판단의 결과 글. 1,000자 이하), `direction`(`오를 것`, `내릴 것`), `predicted_price`, `predicted_reason`(한 줄, 200자 이하), `buy_price`, `sell_price`.
- 답의 줄 표: `견준 결과`, `검증 목록`(1~20줄), `근거`(1~5줄).
  - `견준 결과`(REQ-AI-014): 지난 판단이 있으면 `final_last_report.csv`의 `근거` 줄마다 한 줄씩 꼭 있다(`part`와 `ref_seq`가 그 줄의 `answer_part`와 `seq`). 없으면 0줄이다(8절의 "앞 회차의 결과 보고서가 있을 때만").
  - `검증 목록`(REQ-AI-015): 앞 회차의 목록을 고쳐 쓴 것이다. 줄마다 항목, 믿음, 견준 횟수, 맞은 횟수가 꼭 있다. 앞 회차가 없으면 이번 회차가 처음 만든다(8절). 횟수는 AI가 적는 값이다.

#### 3.8.5 검사와 실패

자료 스레드가 세션 결과를 받으면 `ai/answers.py`의 `judge(result, context) -> Judged`로 가린다. `context`는 마켓 코드, 현재가, 지난 판단과 그 근거 줄이다. 차례대로 보고 처음 걸린 것이 실패 종류다.

1. `TIMEOUT`: 시간 초과. `LIMIT`: 한도 초과. `FAILED`: 3.7.5대로 로그인 만료나 형식 오류.
- 까닭의 글(`Judged`의 까닭. A-17의 내용, 3.11): 정한 글로만 만든다. 표·열·규칙의 이름과 정한 말(예: "search_judgment의 머리줄이 다릅니다.", "final_judgment의 direction이 정한 값이 아닙니다.")이고, 답의 값과 글, Claude Code의 글은 넣지 않는다(3.11.1의 "바깥 글").
2. 검색 판별: 먼저 검색 실패를 본다(다른 검사보다 먼저. 8절). `search_judgment`의 머리줄이 맞고 그 표의 줄에 `search_status`가 `실패`인 줄이 있거나, `search_rows`의 머리줄이 맞고 `출처`의 줄이 0줄이면 검색 실패다. 다른 칸이나 다른 부분의 답이 틀려도 검색 실패가 앞선다. 그다음에 필드가 없거나, 머리줄이 다르거나, 줄 수·값·코인 코드가 3.8.1~3.8.2와 다르거나, `judgment`가 두 값이 아니면 형식 오류다(REQ-AI-029).
3. 봉 판별: 같은 꼴로 형식 오류.
4. 2나 3이 실패이면 최종 예측의 답은 있어도 보지 않고 버린다(REQ-AI-013. 코인 세션에도 부르지 말라고 지시한다. 3.7.2).
5. 최종 예측(형식 오류): 필드가 없음, 머리줄이 다름, 코인 코드가 다름(어느 표의 어느 줄이든), `direction`이 빠졌거나 두 값이 아님(REQ-AI-010), `predicted_price`나 `predicted_reason`이 없음(REQ-AI-011), 가격이 0 이하이거나 수가 아님, 예측 가격이 방향 예측과 반대쪽(REQ-AI-012), 꼭 있어야 하는 제안가가 없음('오를 것'이면 `buy_price`, '내릴 것'이면 `sell_price`. REQ-AI-032), 지난 판단이 있는데 `result_text`가 비었음, `견준 결과`가 지난 판단의 근거 줄과 하나씩 맞지 않음(빠짐, 겹침, 없는 번호), `검증 목록`이 0줄이거나 값이 틀림, 줄 수나 글의 길이가 넘침.
   - 반대쪽: 기준은 최종 예측에 준 현재가 P다(8절, REQ-AI-028). '오를 것'인데 예측 가격 < P, '내릴 것'인데 예측 가격 > P이면 실패다. 같으면 통과다. 예(만든 값): P 100, '오를 것', 예측 99는 실패, 100과 101은 통과다.
- 실패이면 보고서는 `FAILED`이고, 그 회차의 답은 정상으로 받은 판단이 아니다(8절). 실패한 보고서의 답은 여섯 표 가운데 머리줄이 맞는 표만 저장해 둔다(판단 표는 `reports`의 칸, 줄 표는 `report_rows`). 머리줄이 다른 표와 필드가 없는 표는 저장하지 않는다. 머리줄이 맞는 줄 표에서도 정수 칸(`seq`, `ref_seq`, `compared`, `hits`)이 정수가 아니거나 `text`가 빈 줄은 STRICT 표에 넣을 수 없으므로 저장하지 않는다. 줄 표에서 (`answer_part`, `kind`, `seq`)가 앞 줄과 겹치는 뒤 줄은 버린다(`report_rows`의 키에 걸려 `StorageError`가 나면 A-29로 AI가 꺼지기 때문이다. 3.5.4의 "실행기가 알린 실패는 끄지 않는다"와 맞춘다). 화면에는 보이지 않는다(3.12.1).
- 정상이면 세 부분의 판단과 줄 표를 부분마다 따로 저장하고(`report_rows.answer_part`. REQ-AI-002) `OK`다. 그 판단이 다음 회차의 "지난 판단"이 된다.
- 장기·단기 의견을 담을 열은 어느 표에도 없다(REQ-AI-023).

### 3.9 지난 판단의 결과(프로그램이 셈하는 값. 8절)

- 지난 판단: 그 코인, 그 모드에서 이번 회차보다 앞의 `OK` 보고서 가운데 T가 가장 늦은 것이다(8절의 "가장 최근에 정상으로 받은 판단").
- 예측 가격이 가리킨 때: 지난 판단의 T + 단위의 길이(그 판단의 다음 회차 때)다. 그 다음 회차가 실제로 돌았는지와 상관없이 이 때다.
- 실제 값: 지난 판단의 단위의 봉 가운데 시작 시각이 지난 판단의 T인 봉(곧 예측이 가리킨 때에 끝나는 봉)의 종가다. 그 봉이 저장되어 있고 완성되어 있을 때만 있다. 없으면(봉 단위를 바꿔 지워짐, 꺼져 있어 받지 못함 등) `None`이고, 차이와 맞았는지도 `None`이며 화면은 "-"다(설계서 5.2의 "값이 없으면 '-'").
- 차이: 실제 값 ÷ 예측 가격 − 1의 비율이다. 0.0001 단위로 맞춘다(`ROUND_HALF_EVEN`. M1 명세 3.5). 양수면 실제가 예측보다 높다. 화면은 부호를 붙인 소수 둘째 자리까지의 백분율이다(`format_percent(…, signed=True)`).
- 맞았는지(REQ-AI-028): 기준은 지난 판단에 준 현재가 P다. '오를 것'은 실제 값 ≥ P이면 맞음, < P이면 틀림이다. '내릴 것'은 실제 값 ≤ P이면 맞음, > P이면 틀림이다(같으면 둘 다 맞음).
- 예(만든 값): P 100, '오를 것', 예측 가격 102.
  - 실제 값 101: 차이 101 ÷ 102 − 1 = −0.009803…이므로 −0.0098(화면 "-0.98%"), 맞음.
  - 실제 값 99: 차이 −0.0294, 틀림. 실제 값 100: 차이 −0.0196, 맞음.
  - 같은 P와 실제 값 100에 '내릴 것'이어도 맞음이다.
- 쓰는 곳: 이번 회차의 입력(`final_last_judgment.csv`. REQ-AI-019, REQ-AI-020의 "실제 가격(봉)을 확인해"), 이번 보고서의 '지난 판단의 결과'(REQ-AI-018)와 그 저장(3.10). 함수는 `ai/last_result.py`의 `compute_last_result(judgment, candle_close) -> LastResult`이고 계산만 한다. 봉은 `app`이 `storage`에서 읽어 넘긴다.

### 3.10 저장(`storage/`, 스키마 2)

- 스키마 올리기: `SCHEMA_VERSION = 2`다. 표는 STRICT다. 2보다 크면 지금처럼 `StorageError`다. 표와 열을 지우거나 바꾸지 않는다.
  - 가르는 법: `migrate`는 트랜잭션(`storage/database.py`의 `transaction`. `BEGIN IMMEDIATE`)으로 잠근 뒤 다시 읽은 번호로 가른다. 0이면 `_SCHEMA_1`과 1→2 묶음을, 1이면 1→2 묶음만 돌리고, 2면 아무것도 하지 않는다. `_SCHEMA_1`은 바꾸지 않는다. 지금 코드처럼 번호가 작을 때 `_SCHEMA_1`을 모두 돌리면, v0.1.0의 DB(`user_version` 1)에서 `CREATE TABLE settings`가 실패해 켜기의 A-29로 앱이 뜨지 않는다.
  - 1→2 묶음: 표 셋(`rounds`, `reports`, `report_rows`)의 `CREATE TABLE`과 `ALTER TABLE alerts ADD COLUMN report_id INTEGER`(열은 끝에 붙고 기존 줄은 NULL)다. 0에서도 `_SCHEMA_1` 뒤에 같은 묶음을 돌리므로, `alerts.report_id`는 0→2와 1→2 모두 맨 끝 열이고 여섯 표의 `PRAGMA table_info`가 두 길에서 같다.
  - 트랜잭션: DDL과 번호 쓰기는 모두 그 한 트랜잭션 안에서 `conn.execute`로 한다. `executescript`는 쓰지 않는다(열린 트랜잭션을 먼저 커밋하므로 중간에 실패해도 앞의 표가 남는다). `IF NOT EXISTS`는 쓰지 않는다(있으면 번호와 맞지 않는 DB이므로 실패해야 한다). 번호는 끝에 `PRAGMA user_version=2`로 한 번 쓴다. 중간에 실패하면 번호도 표도 남지 않고 `StorageError`다.
  - 3단계의 2→3(M3 명세 3.12)도 같은 꼴이다: 잠근 뒤의 번호가 0이면 `_SCHEMA_1`, 1→2, 2→3을, 1이면 1→2와 2→3을, 2이면 2→3만 돌린다.
  - CHECK를 걸지 않는 열: 지금 코드는 열거 값의 열에 열거형에서 만든 CHECK를 건다(`alerts.discord_state`). 세 표에서는 아래 열에 CHECK를 걸지 않는다(타입은 STRICT 그대로다).
    - `rounds.state`, `reports.state`: 3단계가 값 `discarded`를 더한다(M3 명세 3.12).
    - `rounds.trigger`: 4단계가 값 `missed`를 더한다(M4 명세 3.10.2). 걸면 2·3단계의 exe가 만든 사용자의 DB에 그 제약이 남아 4단계의 `missed` 쓰기가 실패한다.
    - `reports`의 판단 칸(`search_judgment`, `search_status`, `candle_judgment`, `direction`, `last_hit`)과 `report_rows`의 값 칸(`answer_part`, `kind`, `part`, `verdict`, `belief`): 머리줄이 맞는 실패한 답은 "보류" 같은 값도 저장하므로(3.8.5), CHECK가 있으면 그 저장이 A-29가 되어 AI가 꺼진다.
- 표 `rounds`:
  - `id INTEGER PRIMARY KEY AUTOINCREMENT`, `mode TEXT NOT NULL`, `number INTEGER NOT NULL`, `trigger TEXT NOT NULL`(`RoundTrigger` 값. 2단계는 `bar_close`뿐이다), `unit TEXT NOT NULL`, `close_utc TEXT NOT NULL`(T), `next_utc TEXT NOT NULL`, `started_utc TEXT NOT NULL`, `ended_utc TEXT`, `state TEXT NOT NULL`(`running`, `done`, `interrupted`).
  - `UNIQUE (mode, number)`.
- 표 `reports`:
  - `id INTEGER PRIMARY KEY AUTOINCREMENT`, `round_id INTEGER NOT NULL REFERENCES rounds(id)`, `mode TEXT NOT NULL`, `market TEXT NOT NULL`, `state TEXT NOT NULL`(`ReportState` 값), `failure TEXT`(실패 종류, 쉰 까닭, 오류 이름의 글).
  - `base_price TEXT`, `price_read_utc TEXT`.
  - `search_judgment TEXT`, `search_status TEXT`, `candle_judgment TEXT`, `direction TEXT`, `predicted_price TEXT`, `predicted_reason TEXT`, `buy_price TEXT`, `sell_price TEXT`, `result_text TEXT`.
  - `last_report_id INTEGER`(견준 지난 판단의 보고서), `last_predicted_price TEXT`, `last_actual_price TEXT`, `last_diff TEXT`, `last_hit TEXT`(3.9의 값. 그 회차에 셈한 것).
  - `input_tokens INTEGER`, `output_tokens INTEGER`, `cache_read_tokens INTEGER`, `cache_creation_tokens INTEGER`, `model_tokens TEXT`(`[{"model": …, "input_tokens": …, "output_tokens": …, "cache_read_tokens": …, "cache_creation_tokens": …}]` 꼴의 JSON 글. 키는 `ModelTokens.model`과 `TokenUsage`의 필드 이름과 같다).
  - `tools_used TEXT`: 칸마다 쓴 도구의 이름(3.7.5의 `SessionResult.tools`). `{"session": ["Agent"], "search": ["Read", "WebSearch"], "candle": ["Read"], "final": ["Read"]}` 꼴의 JSON 글이고 키는 `AiSlot` 값이다. 도구의 이름만 담고 입력 값과 검색어는 담지 않는다. 세션을 띄우지 않은 보고서는 NULL이다.
  - `elapsed_report_s INTEGER`, `elapsed_order_s INTEGER`(2의 4), `created_utc TEXT NOT NULL`, `finished_utc TEXT`.
  - `UNIQUE (round_id, market)`. 가격은 `Decimal`의 글이다(M1 명세 3.7).
- 표 `report_rows`:
  - `report_id INTEGER NOT NULL REFERENCES reports(id)`, `answer_part TEXT NOT NULL`(`AiSlot`의 세 부분 값), `kind TEXT NOT NULL`, `seq INTEGER NOT NULL`, `part TEXT`, `ref_seq INTEGER`, `text TEXT NOT NULL`, `url TEXT`, `verdict TEXT`, `belief TEXT`, `compared INTEGER`, `hits INTEGER`.
  - `PRIMARY KEY (report_id, answer_part, kind, seq)`. 열은 3.8.1의 줄 표와 같다.
  - 화면 값으로 읽기(5번): `kind`의 글은 `core/ai.py`에 5번이 더하는 `RowKind`(`StrEnum`: `EVIDENCE="근거"`, `SOURCE="출처"`, `COMPARED="견준 결과"`, `CHECKLIST="검증 목록"`)의 값이다. `storage`는 `ai`를 import하지 못하므로(`scripts/checks/import_rules.py`) `core`에 두고, 9번의 `ai/`도 같은 값을 쓴다. `answer_part`는 `AiSlot`의 값이다.
    - `견준 결과` 줄의 `part`에는 한글 부분 이름(`검색 판별` 등. 3.8.1)이 들므로 `AI_SLOT_TITLES`를 거꾸로 써서 `ComparedItem.part`(`AiSlot`)에 담는다. `ComparedItem.seq`에는 `ref_seq`(앞 회차 근거의 번호. 3.12.1의 "{부분 이름} {번호}")를 담는다.
    - `EvidenceItem`은 `answer_part`·`seq`·`text`, `SourceItem`은 `seq`·`text`(제목)·`url`, `ChecklistItem`은 `seq`·`text`·`belief`·`compared`·`hits`다.
    - `LastResult.round_number`: `reports`에 열이 없으므로 `last_report_id`의 보고서의 `round_id`로 `rounds.number`를 이어 읽는다.
- 표 `alerts`에 더하는 열: `report_id INTEGER`. A-26이 가리키는 보고서의 `reports.id`이고, 다른 알림은 NULL이다. 읽어서 `AlertView.report_id`에 담는다(3.12.6). 쓰기는 `storage/alerts.py`의 `insert_alert`에 키워드 인자 `report_id: int | None = None`을 더해 한다(5번. 지금 부르는 곳인 `app/data_thread.py`와 `app/startup_errors.py`는 키워드로 부르므로 그대로 돈다). 읽는 열(`_COLUMNS`)에도 더한다.
- 설정 키(표 `settings`):
  - `ai_model:{칸}`, `ai_effort:{칸}`: `AiSlot` 값마다. 값은 `CLAUDE_MODELS`의 하나, `Effort` 값이다. `storage/settings.py`가 읽는 키 목록(`SELECT … WHERE key IN …`)에 여덟 키를 더한다.
    - 읽기: 틀린 값(목록에 없는 모델이나 노력 값)이 든 칸만 저장되지 않은 것으로 보고 버린다. 모델과 노력이 둘 다 맞는 칸만 `AiSlot`의 차례로 `SettingsView.ai_choices`에 담는다. ai 키 때문에 `StorageError`를 내지 않는다(지금의 다른 키처럼 내면 켤 때 설정 전체를 읽지 못한 것이 된다. `app/data_thread.py`의 설정 읽기).
    - 쓰기: `ai_choices`가 `None`이거나 빈 튜플이면 ai 키를 쓰지도 지우지도 않는다(자료 스레드는 저장할 때마다 빈 튜플을 넘긴다). 네 칸(`AiSlot` 넷이 하나씩)이 아닌 묶음은 버리고 다른 값만 저장한다. 이때 `ValueError`를 내지 않는다(내면 자료 스레드가 A-30을 만든다). 네 칸이면 여덟 키를 그 저장의 같은 트랜잭션에서 쓴다.
  - 놓친 회차가 쓰는 키는 4단계가 더한다.
- 회차의 기록(REQ-AI-006, REQ-AI-025의 수용 기준): `reports.tools_used`다. 웹 페이지 본문을 여는 도구(`WebFetch`)가 어느 칸에도 없는지, `WebSearch`가 검색 판별 칸에만 있는지(검색 판별 칸은 `Read`와 `WebSearch`), 봉 판별과 최종 예측 칸에 `Read`만 있는지를 이 값으로 본다. 앱은 이 값으로 보고서를 실패로 가르지 않는다.
- 지우지 않는 것: 보고서, 회차, 줄 표는 알림 보관 기간과 손으로 지우기로 지우지 않는다(11절). 지우는 기능은 없다.
- 자료의 형식(REQ-DATA-010): 2단계가 저장하는 자료는 모두 위의 열이 정해진 SQLite 표이고, AI와 주고받는 파일은 3.8의 CSV다. 세션 폴더의 파일은 세션이 끝나면 지운다(3.7.2). md 파일로 된 자료는 없다.
- 쓰기와 읽기의 함수: 세 표의 쓰기와 읽기 함수는 모두 5번이 `storage/`에 만들고, 15번은 부르기만 한다.
  - 쓰기: 회차 쓰기(시작, 끝과 상태 고쳐 쓰기), 보고서 쓰기(`RUNNING`으로 만들기, `OK`·`FAILED`·`SKIPPED`·`ERROR`·`INTERRUPTED`로 고쳐 쓰기와 판단 칸·토큰·걸린 시간·`tools_used`), 줄 표 쓰기(3.8.5의 겹치는 뒤 줄 버리기 포함), 끊긴 회차 정리(`running`을 `interrupted`로, `RUNNING`을 `INTERRUPTED`로). 한 보고서의 판단 칸과 줄 표는 한 트랜잭션에서 쓴다.
  - 읽기: 보고서 목록(그 코인, 그 모드, 새것부터 `REPORT_LIST_LIMIT`개), 보고서 하나와 그 줄 표, 지난 판단(3.9), 회차의 `RUNNING` 보고서가 있는지, 그 모드의 가장 큰 회차 번호. 읽기는 `RoundItem`, `ReportListView`의 줄, `ReportView`, `LastResult`를 만들어 돌려준다.
- `OK`가 아닌 보고서: 판단 표의 칸(`search_judgment`, `candle_judgment`, `direction`, 가격, 까닭, `result_text`), 지난 판단의 결과, 줄 표를 `RoundItem`·`ReportView`에 담지 않는다(`None`, 빈 튜플). 실패한 답에는 "보류", "중립" 같은 값이 저장될 수 있어(3.8.5), 열거형으로 바꾸다 실패하면 `load_reports`가 깨지기 때문이다. 저장된 값은 그대로 두고 화면에 보이지 않는다(3.12.1). 이것은 5번의 읽기가 화면 값을 만들 때 한다.

#### 3.11.1 문제 보고 표(제품 규칙 12절, 14절, REQ-DATA-011)

분류가 오류 알림과 기타 알림인 알림을 열이 정해진 CSV로 자료 폴더에 쌓는다. 운영 자동화(제품 규칙 14절)에서 지휘 세션이 읽는 것은 이 폴더의 파일뿐이다. 아래의 자리, 꼴, 쓰는 때, 열은 사용자의 뜻("문제 보고 표 열도 지금 정해서 진행")을 따라 지휘가 정한 기본값이다. 이 절은 그것에 타입, 함수, 맡는 팀, 시험을 붙인다. 맡는 팀은 백엔드이고, 새 모듈 `app/problem_report.py`(21번)에 둔다. 쓰는 것은 자료 스레드다.

- 자리: 자료 폴더 `root`(M0 명세 3.5) 아래 `problems\problems-YYYY-MM.csv`다. `YYYY-MM`은 그 줄의 `occurred_kst`의 한국 시간 달이다(달마다 한 파일). 폴더가 없으면 만든다.
- 남기는 파일: 켤 때(M1 명세 3.8의 켤 때 차례 3의 앞) 자료 스레드가 `problems` 폴더에서 이름이 `problems-YYYY-MM.csv`이거나 그 뒤에 `.bad`가 붙은 파일 가운데, 지금의 한국 시간 달과 그 앞 두 달(가장 최근 3개월)이 아닌 달의 파일을 지운다. 그 밖의 이름은 건드리지 않는다. 예(만든 값): 지금이 한국 시간 2026-12-05이면 `problems-2026-10.csv`, `problems-2026-11.csv`, `problems-2026-12.csv`가 남고 `problems-2026-09.csv`와 `problems-2026-08.csv.bad`는 지워진다.
- 꼴: 3.8.1의 공통 꼴(UTF-8 BOM, 쉼표, CRLF, 첫 줄은 머리줄)이다. 파일이 없으면 BOM과 머리줄부터 쓴다. 덧붙일 파일의 첫 줄이 `PROBLEM_COLUMNS`의 머리줄과 다르면, 그 파일의 이름 뒤에 `.bad`를 붙여 두고(같은 이름의 `.bad`가 있으면 그것을 덮는다) 새 파일을 머리줄부터 쓴다.
- 쓰는 때: 분류가 `AlertCategory.ERROR`나 `OTHER`인 알림이 알림 표에 생길 때마다 그 줄을 쓴 뒤 한 줄을 덧붙인다. 켤 때 `startup-errors.jsonl`에서 옮긴 알림(M1 명세 3.9)도 같다. 표에 쓰지 못해 메모리에 둔 알림(M1 명세 3.9의 메모리 알림)도 그 음수 번호로 한 줄을 쓴다. 되풀이(M1 명세 3.9, 3.11)로 만들지 않은 알림도 그때 한 줄을 쓴다: `alert_id`는 빈 칸이고(알림 표에 줄이 없다), 나머지 칸은 만들었다면 생겼을 알림의 값이다. 그래서 같은 문제가 되풀이되면 `repeat_24h`가 는다(REQ-DATA-011의 수용 기준). 다른 분류(보고서 알림의 A-26 등)는 쓰지 않는다.
- 실패: 덧붙이기, 폴더 만들기, 지우기, 이름 바꾸기가 실패하면(`OSError`) 로그에만 가린 글로 남긴다. 알림을 만들지 않고, 회차와 다른 일을 막지 않는다. 다음 알림에서 다시 쓴다(빠진 줄은 다시 쓰지 않는다).
- `--self-test`는 이 폴더와 파일을 만들거나 쓰지 않는다. 시험은 자료 폴더를 `tmp_path`에 둔다(`tests/conftest.py`의 지금 장치).
- 열(`PROBLEM_COLUMNS`. 이 차례 그대로):

| 열 | 뜻 | 값 |
|---|---|---|
| `alert_id` | 알림 번호 | 알림 표의 `id`(정수. 메모리 알림이면 그 음수, 되풀이로 만들지 않은 알림이면 빈 칸) |
| `occurred_kst` | 일어난 때 | 한국 시간, `2026-11-22T03:15:20+09:00` 꼴. 알림의 `created_utc`를 `KST`(M1 명세 3.4)로 바꾸고 초까지 적는다 |
| `app_version` | 판 번호 | 앱 화면과 같은 꼴(예: `v0.2.0`. 제품 규칙 10절). `"v"`에 루트의 `__version__`을 붙인 글이다 |
| `mode` | 모드 | 알림 표의 `mode`와 같은 값(`Mode`의 값. 2단계는 `paper`) |
| `category` | 분류 | `오류`, `기타`(`ERROR`, `OTHER`) |
| `code` | 알림 종류 | 알림 표의 `code`(예: `A-30`) |
| `stage` | 단계 | 알림 표의 `stage`(없으면 빈 칸) |
| `error_name` | 오류 이름 | 알림 표의 `error_name`(없으면 빈 칸) |
| `source` | 일어난 자리 | 아래 "일어난 자리" |
| `coin` | 코인 | 알림 표의 `coin`(없으면 빈 칸) |
| `round_number` | 회차 번호 | 그 알림이 난 회차의 번호(없으면 빈 칸). 아래 "회차 번호" |

| `fingerprint` | 같은 문제의 표시 | `code`, `stage`, `error_name`, `source`를 `\|`로 이은 글(없는 칸은 빈 글)을 UTF-8로 sha256한 값의 앞 12자(16진수 소문자) |
| `message` | 가린 내용 | 아래 "가린 내용" |

- 타입과 함수(`app/problem_report.py`):
  - `PROBLEM_COLUMNS`: 위 열 이름의 튜플. `ProblemRow`(frozen dataclass)는 같은 이름, 같은 차례의 필드를 갖는다(`alert_id: int | None`, `round_number: int | None`, `repeat_24h: int`, 나머지는 `str`이고 빈 칸은 빈 글).
  - `problem_source(exc: BaseException | None, module: str) -> str`, `problem_fingerprint(code, stage, error_name, source) -> str`, `problem_message(text, content, *, secrets, env) -> str`.
  - `ProblemReport(root: Path)`: `prune(now: datetime) -> None`(남기는 파일), `append(row: ProblemRow) -> None`(머리줄 확인과 덧붙이기. 실패는 `OSError`), `count_recent(fingerprint: str, occurred: datetime) -> int`(그 달과 앞 달의 파일에서, `occurred_kst`가 `occurred`의 24시간 전보다 뒤이고 `occurred` 이하이며 `fingerprint`가 같은 줄의 수. 이 줄은 세지 않는다). `repeat_24h`는 `count_recent(…) + 1`이다. 켤 때 읽은 값을 메모리에 두어도 되지만 결과는 파일로 센 것과 같아야 한다.
  - 지금 코드에 `problem`으로 시작하는 이름은 없다(겹치지 않는다).
- 일어난 자리(`source`): 알림이 예외에서 생겼으면 그 예외의 traceback에서 앱 패키지(`coin_report_trader`) 폴더 안의 파일인 마지막 자리를, 패키지 폴더에 대한 상대 경로(`/`로 잇는다)와 줄 번호로 쓴다(예: `ai/claude_cli.py:142`). 예외가 없거나 예외가 앱 밖(표준 라이브러리, 외부 패키지, 시험의 가짜)에서만 났으면, 알림을 만든 모듈의 이름에서 앞의 `coin_report_trader.`를 뗀 것이다(예: `app.data_thread`). 절대 경로와 사용자 폴더는 어느 쪽에도 쓰지 않는다.
  - 옮긴 알림: 21번부터 `startup-errors.jsonl`의 줄에 키 `source`를 더해 같은 규칙의 값을 쓴다. 옮길 때 그 값을 쓰고, 키가 없는 앞의 줄이면 `app.startup_errors`다.
- 회차 번호(`round_number`): 회차의 `rounds` 줄을 쓴 뒤(3.5.2의 3 뒤) 그 회차 안에서 만든 알림(A-2, A-17, A-18, 회차 안의 A-29·A-30)만 그 회차의 `number`를 담는다. 회차를 쓰기 전에 만든 알림((라)의 받기의 A-1, 3.5.2의 2의 A-19)과 회차 밖의 알림은 빈 칸이다.
- 가린 내용(`message`): 알림의 글(`text`)과, 내용(`content`)이 있으면 ` · ` 뒤에 내용을 이은 한 줄이다. 차례대로 아래를 거친다.
  1. `redact`(M1 명세 3.10. 비밀 값, 웹후크 주소, 사용자 폴더의 경로).
  2. IP 주소를 `(가려서 보임)`으로 바꾼다: 점으로 이은 0~255의 수 넷(IPv4), `::`가 들었거나 16진수 글자(a~f)가 하나 이상 든, `:`로 이은 16진수 묶음 셋 이상(IPv6). 시각 글(`10:30:00`)은 16진수 글자도 `::`도 없으므로 바뀌지 않는다.
  3. 남은 절대 경로를 `(경로)`로 바꾼다: 드라이브 글자로 시작하는 경로(`C:\…`, `C:/…`), `\\`로 시작하는 경로, 낱말이나 `:`·`/` 바로 뒤가 아닌 `/`로 시작해 `/`가 하나 더 든 경로. 빈칸까지가 한 경로다. 주소(`https://…`)의 `/`는 바꾸지 않는다.
  4. 줄바꿈(`\r\n`, `\n`, `\r`)과 탭을 빈칸 하나로 바꾸고, 앞에서부터 500자에서 자른다.
- 넣지 않는 것(제품 규칙 12절): 잔고, 주문 금액, 주문 번호와 식별자, 키, 웹후크 주소, IP 주소, 사용자 폴더 경로와 절대 경로, 계정 정보. 열은 위의 열넷뿐이고 금액, 잔고, 주문을 담는 열은 없다. `message`는 알림의 `text`와 `content`로만 만든다. 금액이나 잔고를 담는 알림의 칸(3단계부터의 매매 알림의 금액 등)은 옮기지 않는다. 2단계의 오류 알림과 기타 알림의 글과 내용에는 그런 값이 없다. 3단계부터 그런 값을 글에 담는 오류 알림이 생기면 그 단계의 명세가 그 값을 `message`에서 빼는 법을 정한다.
- 바깥 글을 넣지 않는다: 지휘는 이 표를 읽고 팀 과제를 만들므로(제품 규칙 14절), AI의 답, 웹 검색, `claude`의 표준 오류에서 온 글이 알림의 글과 내용에 들지 않게 한다. A-17의 까닭은 정한 글(3.8.5), AI의 답을 다루다 난 A-30의 내용은 예외 종류와 자리(3.11), 실행기의 `detail`은 로그에만 쓴다(3.13). 그래서 `message`에 그런 글이 들지 않는다(C32).
- 예(만든 값): 2026-11-21T18:15:20Z(한국 2026-11-22 03:15:20)에, 판이 `v0.2.0`이고 회차 7 안에서 `KRW-AAA`의 실행기가 `RuntimeError("boom")`을 냈다. 예외의 앱 안 마지막 자리는 `app/ai_threads.py:57`이다. 이때 A-30(번호 41)의 줄은 `41,2026-11-22T03:15:20+09:00,v0.2.0,paper,기타,A-30,AI 보고서,RuntimeError,app/ai_threads.py:57,KRW-AAA,7,1,13914e95324f,예상하지 못한 오류가 났습니다(RuntimeError). · boom`이다. `fingerprint`는 `A-30|AI 보고서|RuntimeError|app/ai_threads.py:57`의 sha256 앞 12자다. 같은 문제가 23시간 뒤에 다시 쓰이면 그 줄의 `repeat_24h`는 2, 25시간 뒤이면 1이다.

#### 3.12.2 모델·노력 값 칸(설계서 3.2의 9, 6.2의 4)

- 자리: 처음 설정은 3.2의 9의 "Claude 모델*" 자리, 설정은 6.2의 4("일정과 모델")의 자리다. 봉 단위·봉 개수 칸(M1 명세 3.14.1) 뒤에 둔다.

- AI에 주는 것은 3.8의 입력 파일과 두 판별의 답뿐이다. 업비트 키, 잔고, 주문 내역, 계정 정보, 웹후크 주소, 자료 폴더의 다른 파일, 로그는 주지 않는다. 원본 봉은 주지 않는다(REQ-AI-007). 2단계의 매매 기록 요약은 빈 표다.

  - "주어진 파일 말고 다른 파일을 읽지 않는다. 웹 페이지의 본문을 열지 않는다."

### 3.14 `--self-test`, 의존성, 패키징

- `--self-test`는 `claude`를 부르지 않고 네트워크를 쓰지 않는다. 항목은 일곱 그대로이고 마지막 줄은 `결과: 통과 (7/7)`이다. 바뀌는 것은 둘이다: `import` 점검의 `SUBPACKAGES`에 `ai`를 더한다(15번). `sqlite` 점검(`app/self_test.py`의 `check_sqlite`)은 지금 `version != 1`과 표 셋의 이름(`settings`, `candles`, `alerts`)을 박아 두었으므로, 5번이 `SCHEMA_VERSION`(2)과 표 여섯(`settings`, `candles`, `alerts`, `rounds`, `reports`, `report_rows`)을 보게 고치고, 그 시험(`tests/unit/test_self_test.py`의 "스키마 번호 1", "표 3개")의 기대값을 "스키마 번호 2", "표 6개"로 고친다. 고치지 않으면 5번 뒤 windows 검사의 `--self-test`가 실패한다.
- 새 런타임 의존성은 없다(`subprocess`, `csv`, `json`, `shutil`, `ctypes`는 표준 라이브러리). 그래서 `pyproject.toml`과 `uv.lock`은 판 올리기(23번)만, `packaging/`은 안내 문서를 묶음에 넣는 25번만 고친다. `ai`는 `collect_submodules`로 번들에 든다. 빌드나 `--self-test`가 번들 때문에 실패하면 그 번호는 BLOCKED 초안 PR로 멈추고 품질·빌드가 고친다(M1 명세 4절의 규칙).
- 판 올리기(23번. REQ-MAINT-009, REQ-MAINT-010): 2단계 끝의 판은 0.2.0이다. `pyproject.toml`의 `version`과 `uv.lock`의 이 프로젝트 줄, 루트의 `__version__`을 `0.2.0`으로 한다. Windows 실행 파일의 판 정보(제품 판·파일 판 글 `v0.2.0`, 숫자 칸 0.2.0.0)와 빌드 뒤 확인, `tests/unit/test_version.py`는 M1 명세 59번(3.15)이 만들었고 판 정보를 `__version__`에서 만들므로, 23번은 `packaging/`을 고치지 않고 값과 시험의 기대값만 바꾼다. 상태 줄(3.12.5)과 문제 보고 표의 `app_version`(3.11.1)도 `__version__`을 읽으므로 따로 고치지 않는다. exe 묶음 이름과 Git 태그는 지휘의 일이다(REQ-MAINT-010).

### 3.15 가짜와 시험

- 세션과 CI는 진짜 `claude`를 부르지 않는다. `tests/conftest.py`의 네트워크 차단은 자식 프로세스를 막지 못하므로(그 파일의 글), 시험은 `PATH`의 `claude`를 쓰지 않는다. 실행기의 시험은 실행 명령을 인자로 넘긴다(`ClaudeCodeRunner(sessions_root=…, command=[sys.executable, 가짜 실행 파일])`. 3.4. exe의 명령줄 옵션이나 환경 변수는 두지 않는다).

## 7. 지휘에게 물을 것

물을 것:

1. (정해짐) 안내 글: 저장소의 안내 문서 하나와 앱 안의 도움말 화면, 둘 다 둔다(사용자 결정(2026-11-22)). 3.16과 4절의 25번~28번.
2. 시험한 버전 범위의 상한: 2.2.0 미만으로 두었다(3.7.1). 2단계 실물 시험에서 쓴 버전을 보고 범위를 정해 주기 바란다.

2단계 실물 시험에서 확인할 것(문서로 확인하지 못한 것):

1. 부분마다의 노력 값: 서브 에이전트의 `effort`가 칸마다 실제로 쓰이는지(8절, REQ-AI-004). 안 되면 사용자가 다시 정한다.
2. 부분마다의 토큰량: `modelUsage`는 모델마다라, 부분마다 나눌 수 있는지(REQ-AI-022). 2단계는 세션 전체만 보인다.
3. 주 세션의 도구: `--tools`로 세 도구를 준 세션에서, 주 세션이 스스로 파일을 읽거나 검색하지 않고 서브 에이전트만 부르는지. 막지 못하면 `--agent`로 주 세션에 도구가 `Agent`뿐인 정의를 거는 길을 본다(REQ-AI-025).
4. 서브 에이전트의 `tools`가 세션의 `--tools` 안에서만 고르는지, `search_judge`에 `WebFetch`가 없을 때 페이지 본문을 열지 않는지, 검색 결과에 요약이 오는지(8절, REQ-AI-006).
5. 세션 폴더 밖의 파일 읽기가 `dontAsk`(`--allowedTools`에 `Read` 없음)와 `--restricted`로 실제로 거절되는지(3.7.2). `--restricted` 세션에서 `Agent`와 `WebSearch`, 구독 로그인이 그대로 쓰이는지.
6. 구독 사용 한도에 닿았을 때 `result` 줄의 `is_error`가 참이고 글에 "You've hit your "가 드는지(3.7.5. 문서의 글로 정했다). 다르면 가리는 법을 고친다.
7. 로그인이 끝난 세션이 낸 출력과 `claude auth status`의 끝 코드가 맞는지(3.7.1).
8. Windows에서 `PATH`의 절대 경로 항목만 보는 찾기(3.7.1)가 설치한 `claude.exe`를 찾는지. 찾지 못하면 찾는 자리를 정한다(3.7.1).
9. `--restricted`로 사용자의 Claude Code 설정(`~/.claude`의 훅 등)이 세션에 끼어들지 않는지.
10. 코인 세션이 두 판별의 답을 `structured_output`에 고치지 않고 옮기는지, 판별이 실패했을 때 최종 예측을 부르지 않는지(3.7.2).
11. stream-json의 마지막 `result` 줄에 `structured_output`과 `modelUsage`가 오는지(문서는 json 출력과 Agent SDK의 result 메시지로 적는다), 서브 에이전트의 `tool_use`가 `parent_tool_use_id`와 함께 오는지(3.7.5).
